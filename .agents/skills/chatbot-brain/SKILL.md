# Chatbot Brain

One brain, three channels. All chat logic funnels through a single entry point; the web page, Telegram bot, and embeddable widget are thin adapters around it. Gemini is the LLM, Supabase is the RAG + memory store.

## Architecture — `lib/ai/`

- **`brain.ts`** — `runBrainTurn(input)`, the single entry point every channel calls. Flow: config check → rate limit → get/create `conversations` row → upsert `unified_users` → append user message → load that channel's `model_config` → parallel `retrieveContext` + `getConversationContext` (recent messages + summary) + `getLongTermFacts` + `getActivePromptContent` → `buildSystemInstruction` (persona override + summary block) → Gemini `generateContent` loop (temperature/topP/maxOutputTokens from model_config, max 3 tool iterations) dispatching function calls → persist tool calls + final reply with `model_used`/`tokens_in`/`tokens_out`/`retrieved_chunk_ids`. Returns `{ reply, sessionId, messageId }` — `messageId` is what the web/widget channels attach feedback to.
- **`gemini.ts`** — client setup. `GEMINI_CHAT_MODEL` (default `gemini-flash-latest`, also the fallback in `model-config.ts`), `GEMINI_EMBED_MODEL` (default `gemini-embedding-001`), `EMBEDDING_DIMENSIONS = 768` (Matryoshka-truncated from native 3072 — **must match** `chunks.embedding` column width if either ever changes).
- **`prompt-versions.ts`** — `getActivePromptContent(locale)` / `createPromptVersion(locale, content, createdBy?)` / `clearActivePromptVersion(locale)` / `getPromptVersionHistory()`, backed by `prompt_versions` (one active row per locale, enforced by a partial unique index). `null` active content means "use the hardcoded `DEFAULT_SYSTEM_PROMPT_EN/FA` in `prompt.ts`". 60s cache per locale, invalidated on write. This is what `/admin/settings`'s Persona section edits — every save creates a new version rather than overwriting, so history is never lost.
- **`model-config.ts`** — `getModelConfig(channel)` / `updateModelConfig(channel, update)` / `getAllModelConfigs()`, backed by one `model_config` row per channel (provider fixed to `'gemini'`; temperature/max_tokens/top_p are actually applied to the Gemini call; `fallback_provider`/`fallback_model`/`schedule` are stored but **not evaluated at runtime** — no automatic fallback or time-based switching happens). 60s cache per channel.
- **`embedding-config.ts`** — `getEmbeddingConfig()` / `updateEmbeddingConfig(update)`, backed by the singleton `embedding_config` row (id=1). `chunkSize`/`chunkOverlap`/`topK`/`similarityThreshold` are live-editable from the panel; `provider`/`model`/`dimensions` are shown read-only (changing them would invalidate every stored vector); `rerankerEnabled`/`rerankerModel` are stored but **no reranking step exists**. 60s cache.
- **`retrieval.ts`** — embeds the query, calls Supabase RPC `match_chunks` (joins `chunks`→`documents` for the locale filter) with `top_k`/`similarity_threshold` from `embedding-config.ts`, filters results below the threshold. Returns each match's chunk `id` (needed for `messages.retrieved_chunk_ids`), `content`, `documentTitle`, `similarity`. Fails soft (`[]` on error or nothing clears the bar) — RAG is an enhancement, never a hard dependency.
- **`memory.ts`** — conversation/message/fact persistence against `conversations`/`messages`/`unified_users`/`memory_facts`. `getOrCreateConversation`, `upsertUnifiedUser`, `appendMessage` (returns the new row's id), `getLongTermFacts`/`addLongTermFact` keyed by email, `linkConversationToEmail`. `getConversationContext(conversation, summarizeAfterMessages = 16)` is the summarization gate: below the threshold, full history goes in verbatim; past it, only the last 8 messages (`RECENT_KEEP`) stay verbatim and everything older is folded into `conversations.summary` (regenerated only when `summary_up_to_count` falls behind, not every turn) via `summarize.ts`. The 16-message threshold is a local constant — no table in the new schema has a natural home for it.
- **`summarize.ts`** — `summarizeMessages()`, a plain (non-tool) Gemini call that compresses old turns into ≤5 sentences of English prose, folding forward any prior summary so nothing is lost across repeated compressions.
- **`prompt.ts`** — `buildSystemInstruction(locale, context, facts, {prompt, summary})`. `DEFAULT_SYSTEM_PROMPT_EN/FA` are the exported fallback personas (voice + explicit guardrails: stay in scope, no definitive professional advice, no guaranteed outcomes, hand off when stuck) — used whenever `prompt-versions.ts` has no active row for that locale.
- **`chunk.ts`** — paragraph-aware chunker, `chunkText(text, {chunkSize, chunkOverlap})`. Two knobs, not three — the old target/max split was collapsed to match `embedding_config`'s shape exactly. `DEFAULT_CHUNK_CONFIG` mirrors `DEFAULT_EMBEDDING_CONFIG` for standalone/test use.
- **`ingest.ts`** — `ingestSource`/`ingestSiteCopy`/`ingestCuratedDocs`, called by `scripts/ingest.ts`. Upserts a `documents` row keyed by `(title=sourceKey, locale)` — same id across runs — then deletes+reinserts that document's `chunks`, each with an estimated `token_count` (chars/4, not a real tokenizer). Reads chunk size/overlap from `embedding-config.ts` on each run, so a panel edit takes effect on the next `npm run ingest` with no code change.
- **`feedback.ts`** — `submitFeedback(messageId, rating, comment?)`, backed by `feedback` (rating ∈ {-1, 1}). Called from `app/api/feedback/route.ts` (same-origin: `/chat` page + homepage bubble) and `app/api/widget/feedback/route.ts` (CORS-open, same pattern as `widget/chat`). Telegram has no feedback mechanism.
- **`widget-config.ts`** — `getWidgetConfig()`/`updateWidgetConfig()`, backed by the singleton `widget_config` row (id=1): accent color, corner position, per-locale welcome message override, and `allowedDomains` (empty = every origin allowed, today's default). Also exports `isOriginAllowed(origin, allowedDomains)` and `widgetCorsHeaders(origin, allowedDomains)`, used by every `app/api/widget/*` route to enforce/reflect the allowlist — with no list configured, CORS stays wildcard `*` exactly as before this existed.
- **`tools/`** — `index.ts` (`toolDeclarations` + `dispatchTool`; `ToolContext` = `{conversationId, channel, externalUserId, locale}`), `lead.ts` (`capture_lead` → inserts `leads` with `source=channel`, links email, upserts the visitor's name into `unified_users`), `registration.ts` (`check_registration_status` → queries `registrations`), `handoff.ts` (`request_human_handoff` → inserts `handoff_requests`; fired when a visitor asks for a person or the question is genuinely out of scope).
- **`types.ts`** — `Channel = "web"|"telegram"|"widget"`, `Locale = "en"|"fa"`. `BrainTurnOutput` = `{reply, sessionId, messageId, sources}` — `sources` is the deduped list of `documents.title` the reply drew on, shown on the full chat page.
- **`rate-limit.ts`** — dual-keyed (session + IP) against `rate_limit_hits`. Env: `CHAT_RATE_LIMIT_WINDOW_MINUTES` (default 10), `CHAT_RATE_LIMIT_MAX_MESSAGES` (default 20). Note: a Gemini-side 429 (upstream free-tier quota, not this limiter) still lands *after* the user's message is persisted — a rate-limited turn can leave an orphaned user message with no assistant reply. Hit this constantly while building/testing Parts 1–3 in one day; if `/api/chat` 429s locally with a *fresh* session id and no recent app-level hits in `rate_limit_hits`, it's Gemini's quota, not this limiter — check the dev log for the actual upstream status.
- **`chat-schema.ts`** — shared Zod `ChatRequestSchema` used by both HTTP routes; `getClientIp()`.

`memory.ts` also backs Telegram's `/reset`: `resetConversationContext(conversationId)` sets `conversations.context_reset_at` and clears `summary`/`summary_up_to_count`. `getAllHistory`/`getConversationContext` then exclude anything before that timestamp from what the model sees — nothing is deleted, so the admin conversation viewer (which reads `messages` directly) still shows the full transcript. `findConversation(channel, externalUserId)` is the read-only counterpart to `getOrCreateConversation`, used by `app/api/chat/history/route.ts` so restoring a page's chat history never creates a phantom conversation for a session nobody's used yet.

## Admin panel — `/admin`

Password-gated (`ADMIN_PASSWORD` + HMAC-signed `ADMIN_SESSION_SECRET` cookie, `lib/admin/auth.ts`), outside `app/[locale]/` since it's Roya's own English-only tool. Session cookie path is `/` (not `/admin`) — deliberately, so `app/api/admin/*` route handlers get it too, not just `app/admin/*` pages (a real bug caught 2026-08-11: `path: "/admin"` silently 401'd every settings/handoff API call while the pages themselves loaded fine).

Pages: Overview (stat counts), Leads (+ `source`), Registrations, Conversations (+ per-conversation message viewer showing `model_used`/tokens, close/reopen toggle), Handoffs (resolve toggle), **Broadcast** (Telegram-only mass message: preview recipient count first, then an explicit `window.confirm()` before an irreversible send — see below), Users (`unified_users`, one row per channel identity), Feedback (thumbs up/down with a link back to the conversation), Audit log (every admin action — see below), Settings (four independent sections/save-buttons: **Persona** → `prompt-versions.ts`, **Model** → `model-config.ts` per channel, **Embedding & retrieval** → `embedding-config.ts`, **Embeddable widget** → `widget-config.ts`).

`lib/admin/queries.ts`'s `writeAuditLog(action, target?)` is called from every mutating admin route (`prompt-versions`, `model-config`, `embedding-config`, `widget-config`, `handoffs/[id]`, `conversations/[id]`, `broadcast`) and attributes to `getSeededAdminUserId()` — there's exactly one `admin_users` row (Roya), since the shared-password login isn't a real per-user auth system.

**Broadcast is the one feature in this repo that sends real messages to real people with no undo.** `app/api/admin/broadcast/route.ts` is a single POST endpoint with two modes: without `confirm: true` it's a dry run (returns `recipientCount` only, sends nothing); with `confirm: true` it actually sends, sequentially with a 50ms delay per recipient (Telegram's Bot API rate-limits outbound sends to roughly 30/sec). Recipients are every `unified_users` row with `channel = 'telegram'` — **when testing this locally, never call it with `confirm: true` against the real Supabase project**; there is at least one real person in that table from 2026-08-07 testing, not just synthetic rows from later feature work.

## The three channels

| Channel | Entry point | Notes |
|---|---|---|
| Web | `app/[locale]/chat/page.tsx` → `components/chat/ChatWidget.tsx` → POST `app/api/chat/route.ts` | Session id in `localStorage` key `rv_chat_session_id`. `runtime = "nodejs"`. Same-origin only, no CORS handling. Feedback via `app/api/feedback/route.ts`. History restored on mount via `GET app/api/chat/history/route.ts?channelSessionId=`. Only the `/chat` page (not the homepage bubble) gets starter-question pills and a "Request a consultation" button — both are `ChatWidget` props (`showStarters`, `showConsultationButton`), copy lives in `messages/*.json`'s `chat.starters`/`chat.requestConsultation`/`chat.consultationMessage`. Assistant replies show a "Sources: …" line under the bubble when `BrainTurnOutput.sources` is non-empty. |
| Telegram | `app/api/telegram/webhook/route.ts` | Validates `x-telegram-bot-api-secret-token` header against `TELEGRAM_WEBHOOK_SECRET`. Locale from `from.language_code`. `channelSessionId = chat_id`. Always acks HTTP 200. Replies via `lib/telegram.ts`. Handles `/start`, `/help`, `/reset` (never reach the LLM — see `handleCommand` in the webhook route) and `callback_query` updates from the inline quick-reply row (`quickReplyButtons()`) attached to every reply; a tapped button is answered via `answerTelegramCallbackQuery` then run through the same `handleUserText` path as a typed message. Still no feedback mechanism — Telegram has no equivalent UI primitive wired up. |
| Widget | `app/api/widget/chat/route.ts` + `lib/widget/entry.ts` → bundled to `public/widget.js` | CORS defaults wide open (`Access-Control-Allow-Origin: *`) but narrows to the caller's own origin once `widget_config.allowed_domains` is non-empty (`isOriginAllowed`/`widgetCorsHeaders` in `lib/ai/widget-config.ts`) — a disallowed origin gets a 403 on both the preflight and the real request. Vanilla JS, no React/lib/ai imports — mounts in a Shadow DOM. Session id in `localStorage` key `rv_widget_session_id`. Self-detects API base from its own `<script src>` origin. On mount it fetches `GET app/api/widget/config/route.ts` (always CORS-open — safe, no secrets) to apply the admin-configured accent color, corner, and welcome message before first paint; a fetch failure falls back to the hardcoded defaults rather than breaking the widget. Feedback via `app/api/widget/feedback/route.ts` (same origin-restriction treatment as `widget/chat`). |

All chat/webhook/feedback/history/config routes are forced `runtime = "nodejs"` (not edge) — the Supabase admin client + Gemini SDK are Node-based.

## Supabase schema (`supabase/schema.sql` — source of truth; apply manually in the SQL Editor or via the `mcp__supabase__apply_migration` tool if available, not an automated migration runner)

Rebuilt 2026-08-11 from a spec Roya provided (`documents`/`chunks`/`conversations`/`messages`/`unified_users`/`leads`/`feedback`/`prompt_versions`/`model_config`/`embedding_config`/`admin_users`/`audit_log`) — this **replaced** the original `kb_chunks`/`chat_sessions`/`chat_messages`/`bot_settings` shape via an ID-preserving migration (existing rows kept their ids so every FK still resolved). A few columns exist beyond the spec's literal list because the app needs them to function — each is commented in `schema.sql` at the point it's added (e.g. `documents.locale`, `conversations.summary`/`summary_up_to_count`, `leads.source`).

- **RAG**: `documents` (`source_type`: `site_copy`|`curated_doc`|`pdf`|`docx`|`url`, `source_url`, `status`, `tags text[]`, `locale`; unique on `title,locale`) + `chunks` (`document_id` FK, `content`, `embedding vector(768)`, `token_count`, `chunk_index`, `metadata`; unique on `document_id,chunk_index`) + HNSW cosine index on `chunks.embedding`. RPC: `match_chunks(query_embedding, match_locale, match_count)` joins both.
- **Memory**: `conversations` (unique on `channel,external_user_id`; `status` active/closed, `summary`+`summary_up_to_count` for summarization, `context_reset_at` for Telegram's `/reset`, `locale`, `lead_email`), `messages` (`conversation_id` FK, role: user/assistant/tool, `model_used`, `tokens_in`, `tokens_out`, `retrieved_chunk_ids uuid[]`, `tool_name`/`tool_payload`), `unified_users` (unique on `channel,external_id`; `name`, `first_seen`), `memory_facts` (by email).
- **Tools**: `leads` (`conversation_id` FK, `source` = channel), `registrations`, `handoff_requests` (reason/note/resolved), `feedback` (`message_id` FK, `rating` ∈ {-1,1}, `comment`).
- **Config**: `prompt_versions` (persona=locale key, one active per locale via partial unique index, `created_by` → `admin_users`), `model_config` (one row per channel), `embedding_config` (singleton, id=1), `widget_config` (singleton, id=1 — accent color, corner position, per-locale welcome message, `allowed_domains text[]`).
- **Admin**: `admin_users` (currently one seeded row — see the admin panel section above), `audit_log` (`admin_user_id` FK, `action`, `target`).
- **Other**: `rate_limit_hits`; `contact_messages` (unrelated V1 contact-form table).
- All V2 tables: RLS enabled, zero policies — service-role key only, never exposed to the browser.
- A commented-out "Phase 2" section documents future `profiles`/`services`/`bookings`/`payments`/`webinars` tables — not yet created.

## Deliberately not implemented

Flagged rather than silently skipped — each is stored/scaffolded in the schema or UI but has no runtime effect yet:

- **Cross-provider model fallback / scheduled model switching** — `model_config.fallback_provider`/`fallback_model`/`schedule` exist as columns; nothing reads them.
- **Reranking** — `embedding_config.reranker_enabled`/`reranker_model` exist; no reranking step runs, and the admin UI doesn't even expose a control for it (an unwired toggle would be misleading).
- **PDF/Word/URL ingestion** — `documents.source_type` already allows `'pdf'|'docx'|'url'`, but `ingest.ts` only has adapters for `site_copy` and `curated_doc`. Needs parsing deps (pdf-parse, mammoth, a fetch+extract step) and an admin upload UI.
- **True token-level streaming** — every channel gets a complete reply, not a stream. Telegram can't stream the same way web/widget could (no token-level message editing UX), so this would need per-channel handling, not just a brain-level change. Deferred three separate times across three feature passes (2026-08-11) rather than bolted on as a rushed fourth addition each time — it would mean restructuring `brain.ts`'s tool-calling loop into a stream-aware one, plus SSE plumbing in two routes and stream-consuming rewrites in two different client environments (React state batching in `ChatWidget.tsx`, vanilla DOM manipulation in `lib/widget/entry.ts`). A pulsing typing indicator ships instead as a non-streaming approximation.
- **Real multi-admin auth** — `admin_users` has one seeded row; the actual login is still one shared `ADMIN_PASSWORD`. Every `audit_log` entry attributes to that one row regardless of who used the password.

## Ingest pipeline — [[chatbot-content-sync]]

`npm run ingest` runs `scripts/ingest.ts` (`tsx --conditions=react-server --env-file=.env.local`). Two sources, both delete-then-reinsert per `source_key`+`locale` (idempotent):

1. **Site copy** — `messages/en.json` + `messages/fa.json` namespaces `about`/`aboutPage`/`services`, plus non-draft entries from `content/projects.ts`.
2. **Curated docs** — `content/knowledge/*.md`, filename pattern `<slug>.<locale>.md` → source key `doc:<slug>`. Currently empty aside from a README.

**`Roya_Brand_Guide.md` / `Roya_Brand_Guide_UPDATED.pdf` at the repo root are NOT ingested.** They're the human/design reference used to write site copy — not wired into RAG. If brand-guide content needs to be searchable by the bot, it has to be copied into `content/knowledge/*.md` first.

Re-run `npm run ingest` (and redeploy) whenever site copy, `content/projects.ts`, or `content/knowledge/*.md` changes.

## Deploy checklist

- Env vars (see `.env.local.example`): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_SITE_URL`, `GEMINI_API_KEY` (+ optional `GEMINI_CHAT_MODEL`/`GEMINI_EMBED_MODEL`), `SUPABASE_SERVICE_ROLE_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `ADMIN_PASSWORD` + `ADMIN_SESSION_SECRET` (gates `/admin`), optional rate-limit overrides.
- Site degrades gracefully with zero keys configured — `/chat` shows "not available", contact form falls back to mailto. Don't treat missing keys as a build error.
- `supabase/schema.sql` must be applied manually once (Supabase SQL Editor) — it is not run automatically.
- **After every deploy that changes the public URL**, re-run `npm run telegram:set-webhook -- <public-url>` or the Telegram webhook keeps pointing at the old one.
- `npm run build:widget` (esbuild → `public/widget.js`) runs automatically via `prebuild` before `npm run build`. If bundling manually outside `npm run build`, don't forget it — a stale `public/widget.js` silently serves old widget code to every embedding site.
- Vercel: env vars under Project → Environment Variables; `NEXT_PUBLIC_SITE_URL` must be the production domain there.
